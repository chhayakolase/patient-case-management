Project Abstract

The Smart Patient Case Management System is a full-stack hospital clinical record management web application engineered using Python and Flask. Its primary objective is to replace traditional paper-based clinic registers with a centralized, secure, and digitized repository.

The system enables authorized medical staff to register patients, maintain chronological case histories without overwriting historical records, book appointments with real-time conflict prevention, and generate analytical healthcare reports using Pandas and Matplotlib.

Key Project Objectives
  • Role-Based Staff Access: Ensure only verified healthcare personnel access confidential clinical files.
  • Unified Case History: Maintain sequential medical consultations rather than overwriting past diagnoses.
  • Automated Identifier Generation: Generate unique, structured IDs (e.g. PAT-2026-0001).
  • Doctor Schedule Protection: Prevent overlapping consultation bookings for identical time slots.
  • Data Analytics & Visualizations: Employ Pandas DataFrames and Matplotlib charts for epidemiological tracking.

Common Viva Voce Examination Questions & Model Answers
Prepared for BCA Project Defense

Q1: Why did you choose Flask over Django for this project?

Answer: Flask is a lightweight micro-framework that gives precise control over database connections, routing, and libraries without the heavy boilerplate or ORM overhead of Django. For a BCA project focusing on transparent SQL operations and custom Pandas analytics, Flask is ideal, clean to understand, and easy to present.

Q2: How is password security implemented in your application?

Answer: Passwords are never stored as plain text. We utilize Werkzeug's cryptographic functions — generate_password_hash() during user creation and check_password_hash() during login authentication. Even if the database file is inspected directly, the hashed values cannot be reversed into plain text.

Q3: How do you prevent SQL Injection attacks?

Answer: All database queries in database.py strictly use parameterized queries with ? placeholders rather than raw Python string formatting (e.g. cursor.execute("SELECT * FROM patients WHERE patient_id = ?", (pid,))). This ensures the SQLite database engine treats all user inputs strictly as literal data, completely neutralizing SQL injection exploits.

Q4: How does the system handle medical case history without overwriting previous records?

Answer: We established a normalized 1-to-Many relational structure between the patients and medical_cases tables linked via the foreign key patient_id. Whenever a patient visits for follow-up or a new ailment, a new row is appended to medical_cases. On the patient profile page, all cases are queried ordered by case_date DESC to present an immutable chronological medical timeline.

Q5: How are Pandas and Matplotlib utilized in the Reports module?

Answer: We use Pandas' pd.read_sql_query() to ingest database tables into DataFrames. We apply DataFrame methods such as .value_counts() and pd.cut() to compute frequency breakdowns by age groups and diagnoses. Matplotlib figures are rendered in memory via an io.BytesIO stream using the headless Agg backend, encoded into Base64 strings, and embedded directly into the HTML without saving intermediate image files to disk.

Q6: How does the Appointment Conflict Prevention feature work?

Answer: Before an appointment is saved, the function check_appointment_conflict() queries the appointments table for existing records matching the same doctor_name, appointment_date, and appointment_time with status 'Scheduled'. If a match is found, booking is rejected with an explanatory flash alert, preventing double-booking of doctors.
